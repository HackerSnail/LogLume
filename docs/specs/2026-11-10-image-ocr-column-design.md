# 图片转文字（本地 OCR）+ 列还原 + 选列提取：设计与调研

把截图（台架工具、CAN 分析仪、SCADA/HMI 画面、监控面板、终端日志表格）转成文本，
**保持列结构不变**，再让用户**挑其中一列**的数据取出来。不调用大模型，全程本地离线。

结论：**能做，且不需要大模型。** OCR 是传统 CV 模型（文本检测 + 序列识别），
本地跑得动；真正有难度的是"列还原"、"坐标映射"和"跨平台引擎选型"。列还原已在
`lumelog-core::ocr` 里做完技术验证（§9.3）。

## 0. 已定的决策

| 项 | 决策 |
|---|---|
| 引擎策略 | **混合**：Win/macOS 用系统内置引擎，**PP-ONNX 从"兜底"提升为"保证路径"**——Linux 与"系统内置没有目标语言包"时走 PP-ONNX，且 PP-ONNX 在所有平台都必须可用（§3） |
| 输入范围 | **Phase 1 只做图片文件**（PNG/JPEG 等），不做 PDF 区域框选 |
| 输出落点 | **默认落"新标签页"**：选列结果开成新的文档；后续可加"插入当前光标""替换选区" |
| 模型分发 | **离线组件包**：模型 + ONNX Runtime 原生库打成独立组件，**离线安装，不做运行时联网下载**（§8.1） |
| OCR 运行时 | **`ort`（ONNX Runtime）**，`load-dynamic` 特性，运行时动态加载原生库（§8.1） |
| 运行时依赖集 | **最小集**：v4 mobile det + v4 ch rec + ort 原生库，**det → rec 两段，无 cls、不带 en 单独一套**（§8） |
| 样本 | 验收 corpus = **按公开台架/CAN/SCADA/监控/终端界面造的仿真样本**；另有合成样本专跑 CI 回归（§9） |

这些决策背后是同一逻辑：**体积靠"拆分"解决，不靠重定门槛或牺牲可靠性；可靠性靠
成熟实现 + 真实数据兜底，不靠自研运行时或想象中的样本。** 因此 P6（Windows 安装包
≤15MB）不重定，`ort` 带来的体积由组件包隔离出去。

**唯一必须在交付前盯住的连锁假设**：组件包必须是**离线可装**的。工控现场常常
无外网，如果 PP-ONNX 依赖运行时下载，整条链路的可用性会被一次性拖死——所以
组件包要能在断网的干净机器上装完即用（验证清单见 §8.1）。

## 1. 为什么不需要大模型

- OCR 的工作流是"检测文本框 → 裁剪 → 逐框识别字符"，模型是几 MB 到几十 MB 的
  CNN/CRNN，不是自回归语言模型。没有"理解上下文"这一步，也不需要联网。
- 仓库里已有 AI 面板（OpenAI 兼容接口，`ai.rs`），但这条链路明确不依赖它：
  断网、离线、无 API key 都要能跑。
- 代价要认：OCR 是"看图猜字"，错字率明显高于大模型视觉。对工控场景（信号名、
  数值、单位）够用，对长句散文不够用。

## 2. 输入与输出（Phase 1）

- 输入：图片文件。Rust 侧用 `image` crate 解码（纯 Rust，无原生依赖）。
- 输出：选中的那一列 → `column_text(col)` → **开成新标签页**（可编辑、可保存）。
  同时保留"整表"视图（TSV / 空格对齐），方便核对。

## 3. 引擎策略：混合 + PP-ONNX 为保证路径

### 3.1 三条引擎路线

| 路线 | 中文 | 体积 | 跨平台 | 逐词置信度 | 备注 |
|---|---|---|---|---|---|
| Windows.Media.Ocr | 需 OCR 语言包（中文版 Windows 一般自带 zh-Hans） | 0（系统自带） | 仅 Windows | **无**（`OcrWord` 只有 `Text` + `BoundingRect`） | `windows` crate 有 `windows::Media::Ocr::OcrEngine` |
| macOS Vision | 内置，`recognitionLanguages` 首位给 zh-Hans | 0 | 仅 macOS | 有（`VNRecognizedText.confidence`） | `objc2-vision` 的 `VNRecognizeTextRequest` |
| PP-OCR（ONNX） | 强（开源中文最好那档） | 模型在组件包里 | 三平台一致 | 有（识别器逐行分数） | `ort` + PP-OCRv4 模型（§8） |

三条路线的输出都能统一成"词 + 像素框"，所以引擎可替换，列还原算法与引擎无关。

### 3.2 引擎选择顺序（决策表）

```
用户显式指定引擎？ ──是→ 用它（不可用则报错并列出可用引擎）
        │否
        ▼
目标语言的系统引擎支持？ ──是→ 系统引擎（Win: Windows.Media.Ocr / mac: Vision）
        │否（Windows 缺 zh-Hans 语言包 / Linux 无系统引擎）
        ▼
OCR 组件包已安装？ ──是→ PP-ONNX（ort 动态加载组件里的原生库）
        │否（组件未装；不做运行时下载）
        ▼
降级：系统默认语言引擎（多半是英文）能认多少算多少 + 明确提示
      「中文识别不可用：系统缺 zh-Hans OCR 语言包，OCR 组件包未安装（<组件目录>）」
```

UI 上给引擎切换入口（自动 / 系统内置 / PP-ONNX），便于对比与排障。

## 4. 坐标映射

唯一真值是**原始解码后的图像像素坐标系**（EXIF 方向已归一化）。所有引擎适配层
必须把框还原到这个坐标系，前端只做一次显示缩放。

### 4.1 解码期归一化

- EXIF 方向：`ImageReader::open(path)?.into_decoder()?` → `decoder.orientation()?`
  → `DynamicImage::from_decoder(decoder)?` → `image.apply_orientation(orientation)`
  （`image` 0.25 具备这两个 API）。归一化之后，解码出的像素矩阵与用户看到的方向
  一致，之后所有坐标都基于它。
- 尺寸上限：`Windows.Media.Ocr` 有 `OcrEngine.MaxImageDimension`（运行时读该属性，
  Windows 上通常是 4096）。超限必须先缩放，识别后把框坐标除以缩放系数还原。

### 4.2 引擎坐标系的还原

- **Windows.Media.Ocr**：`OcrResult.TextAngle` 是文字整体倾斜角，而
  `OcrWord.BoundingRect` 落在**去偏斜后**的坐标系里。映射回原图要绕图心做一次
  反向旋转；`TextAngle` 为 0 时直接用。
- **PP-ONNX**：检测输出四点框 → 取轴对齐外接矩形；检测带角度的先按角度校正，
  再把外接框换算到原图坐标。
- **Tesseract**：TSV 的 `left/top/width/height` 已是原图像素（列分析不影响框坐标）。

### 4.3 显示层映射

- dock 里图片按 fit/zoom 显示：`显示坐标 = 原图坐标 × (显示宽 / 原图宽)`。
  HiDPI 的 DPR 只影响 CSS 像素↔设备像素，不参与图片内坐标换算。
- 定义单一映射对象（示例）：`ImageMapping { src_w, src_h, scale }`，提供
  `to_image(x, y)` / `to_display(x, y)`。前端叠加识别框、点选区域都用它，
  不允许各处自己乘系数。
- 取整策略：列边界在**原图坐标**里算完，再按 display scale 缩放到显示层；不在
  显示层做取整，避免误差累积。

### 4.4 验收

- 单测：EXIF 旋转 90°、缩放 0.5、Windows 去偏斜 3° 三个映射用例（用构造的框验证
  往返一致，误差 ≤1px）。

## 5. 识别置信度与纠错

### 5.1 各引擎的置信度能力

| 引擎 | 逐词置信度 |
|---|---|
| Windows.Media.Ocr | **没有**（`OcrWord` 只暴露 `Text` 与 `BoundingRect`） |
| macOS Vision | 有（`VNRecognizedText.confidence`） |
| Tesseract | 有（TSV 逐词 `conf`，0..100；非词层级为 -1） |
| PP-ONNX | 有（识别器逐行/逐字分数） |

统一模型：`WordBox.conf: Option<f32>`（0..=1，`None` = 引擎不提供）。Windows 路径
没有逐词置信度，因此下面的策略必须能在"没有置信度"时退化工作。

### 5.2 阈值与标记

- 逐词低置信阈值默认 0.6（设置可调）；低于阈值的词在 UI 上标黄。
- 整图置信度 = 有置信度时取加权平均；低于 0.5 时提示「识别质量低，建议重新截图」。
- Windows 路径没有置信度 → 退化用**列类型校验**（见下）作为主要质量信号，
  并在 UI 上注明「此引擎不提供置信度」。

### 5.3 纠错手段（都不用大模型）

1. **人工改**：OCR dock 的表格里直接改单元格，保留原值与修改痕迹。
2. **列类型校验**：按列推断类型（整数 / 浮点 / 十六进制 / 布尔 / 时间戳），
   不匹配的单元格标红。工控表格多是数值与 hex，这招比置信度更实用。
3. **易混字符提示**：数值列里出现 `O l I S B Z` 等 → 提示可能混淆；**只提示不自动改**，
   避免把对的改错。
4. **导出时过滤**：可选「只导出高置信单元格」或「低置信行单独列出」。

### 5.4 职责边界

`lumelog-core::ocr` 保持纯函数、**不做任何猜测性修正**；修正与过滤放在 app shell
层。`column_text()` 给的是原样文本。

## 6. 语言包 fallback

- 语言设置：`自动`（默认，跟随系统）/ `简体中文` / `English`，持久化在设置里。
- 检测方式：
  - Windows：`OcrEngine::AvailableRecognizerLanguages` /
    `OcrEngine::IsLanguageSupported(Language)`；
  - macOS：Vision 的 supported recognition languages；
  - PP-ONNX：组件包存在 + `manifest.json` 的 SHA-256 校验通过 + 该语言模型在清单里。
- fallback 链（与 §3.2 一致）：目标语言的系统引擎 → PP-ONNX（组件包已装）→ 系统
  默认语言引擎（多半英文，能认多少算多少）+ 明确提示 → 彻底不可用时报错。
- 提示要具体到可执行：「系统缺 zh-Hans OCR 语言包」/「OCR 组件包未安装，路径
  `<组件目录>`，用离线安装包装上即可」，而不是笼统的"识别失败"，也**不给网络下载
  链接**（工控现场常常无外网）。
- Windows 上装了中文语言包也不代表识别质量够用（截图小字、压缩失真都会掉点），
  所以引擎切换入口始终可用。

## 7. 性能预算

沿用 spec §2 的门槛口径；OCR 是**旁路功能**，不进启动路径，不影响 P1–P6：

| 编号 | 指标 | 建议门槛 | 说明 |
|---|---|---|---|
| P7 | 1920×1080 截图识别耗时 | ≤3s（release，Windows 基准机） | 按引擎分别记；后台线程跑，UI 不卡 |
| P8 | 列还原耗时 | ≤5ms（400×8 表） | 实测 1.72ms，留 3 倍余量 |
| P9 | 识别期间内存增量 | ≤300MB | 1080p 位图约 8MB；模型才是大头 |
| P10 | 主安装包体积（加组件后） | ≤15MB（P6 不重定） | ONNX Runtime 与模型都在组件包里，主包不涨 |
| — | 取消响应 | 取消后 ≤200ms 停止 | 参照 `can_cancel` 的取消通道 |

执行方式沿用仓库既有模式：`spawn_blocking` 里跑，通过 Tauri `Channel` 回传进度
（`doc_chunk`、`can_parse` 都是这个套路），前端可取消。

## 8. OCR 运行时依赖与分发策略

### 8.1 组件包与分发

OCR 运行时依赖收敛为**两个模型 + 一个运行时**：

| 组件 | 文件 | 说明 |
|---|---|---|
| 文本检测 | `ch_PP-OCRv4_det_infer.onnx` | PP-OCRv4 mobile 文本检测模型 |
| 文本识别 | `ch_PP-OCRv4_rec_infer.onnx` | PP-OCRv4 中文识别模型，覆盖中文、英文、数字及常见符号 |
| 推理后端 | `onnxruntime` 本体 | `ort` 动态加载（`load-dynamic` + `ort::init_from`） |

推理管线采用 **det → rec 两段式**，不引入方向分类器，不额外携带英文识别模型，
不使用 server 版检测模型。

- **砍掉方向分类器（cls）**：本功能输入为软件界面截图、PDF 选区、日志/报文/监控
  面板截图，文本方向恒为 upright，不存在拍照/扫描场景中的行级旋转。引入分类器
  只会增加组件包体积和额外推理延迟，影响 P7/P8 耗时指标；同时短数字串在小图块上
  可能被误判为 180°，反而把原本可正确识别的数值认翻，属于主动制造静默错误。
- **不单独携带英文识别模型**：PP-OCRv4 ch 识别模型并非纯中文模型，已覆盖中英文、
  数字及常用符号，能够覆盖台架工具、CAN 报文、SCADA 报表、终端日志、监控面板等
  界面中的混排文本。
- **不使用 server 版检测模型**：本功能主要处理桌面界面截图，分辨率和版面复杂度
  有限，mobile 版检测模型已足够；server 版带来的体积增长对当前场景收益不明显。

相对"v4/v5 各来一套中英 + cls + server det"的贪婪配置，这套把组件包压到**两个
模型 + 一个运行时**，是离线组件包能接受的大小。

**OCR 能力以离线组件包形式交付，不随主包分发。** 组件包需满足：

1. **首装即离线可用**，不做运行时联网下载；
2. **组件包版本与主程序版本强绑定**，加载前校验模型结构、字典和版本兼容性；
3. **组件包发布时附带签名与 checksum**，防止离线拷贝过程中被篡改或截断；
4. 支持**发布页下载、离线拷贝、内网镜像**三种分发渠道——工控/内网场景以内网镜像
   为一等公民。

组件包内容：

    ocr-component-<ver>/
      manifest.json        # 版本、SHA-256 清单、模型清单、签名、许可证
      bin/onnxruntime.dll  # Windows（Linux .so / macOS .dylib）
      models/ch_PP-OCRv4_det_infer.onnx   # 检测（mobile）
      models/ch_PP-OCRv4_rec_infer.onnx   # 识别（ch，中英数一体）

- **主包不装原生库**：只在真正要跑 PP-ONNX 时才 `ort::init_from(...)` 动态加载，
  ONNX Runtime 的体积完全留在组件包里，**主安装包体积不受影响，P6 不重定**。
- **组件缺失时主程序照常启动**：原生库只在调用 PP-ONNX 时才加载，缺失只是
  "该引擎不可用"，不影响编辑器其它功能。
- **完整性**：安装后按 `manifest.json` 校验 SHA-256 与签名，校验不过拒绝启用。

**交付前必须逐条验证的清单**（这条是整条链路的可用性命门）：

1. **断网干净机**：在一台**没有外网**的干净机器上装组件包 → 装完即用，能识别出
   中文表格。这是"离线可装"的硬验证，不是走过场；
2. **三平台各一份**：Windows/Linux/macOS 的原生库名不同，组件包要分别产出；
3. **主包体积**：加完组件后主安装包仍 ≤15MB（P6 不重定，CI 产物检查）；
4. **缺失可用**：不装组件时主程序正常启动，PP-ONNX 选项显示"未安装组件"，提示
   指向本地安装包位置而不是网络下载链接；
5. **模型与许可证**：PP-OCR 模型（Apache-2.0）与 ONNX Runtime（MIT）的版本、来源、
   SHA-256 写进 `manifest.json` 与发布说明。

运行时：`ort`（ONNX Runtime 1.31，成熟实现；`ort` crate 当前 2.0.0-rc.15，许可
MIT OR Apache-2.0）。RC 版本的版本在 `Cargo.lock` 里钉死，ORT 相关代码收在单独
模块里，避免升级牵连其它部分。

### 8.2 升级路径

后续若升级到 PP-OCRv5，按**失败模式**决定替换范围：

- 问题主要表现为**数值认错、字符误识** → 优先替换 **rec** 模型；
- 问题主要表现为**漏检、列缝断裂、小字未检出** → 评估替换 **det** 模型。

det 与 rec 分开升级：v5 首发只换 rec，det 不动（§9.2 的触发判据与之一致）。

## 9. 验收样本与 Phase 0.5

验收 corpus 采用**按公开台架/CAN 工具界面、SCADA/HMI 画面、监控面板、终端/日志/
数据库结果表等版面生成的仿真样本**。仿真样本在生成时需同步产出**逐词像素框**，
用于在 OCR 引擎接入前先行验证列还原与取列逻辑，该部分排入 **Phase 0.5**，位于
组件包与后端实现之前。

为避免理想框掩盖真实 OCR 噪声，**Phase 0.5 的列还原测试必须在理想框基础上注入
位置抖动、框合并/拆分、丢框、噪声框等扰动**，使 CI 提前覆盖真实检测框的脏数据
分布。

### 9.1 仿真样本版面来源

仿真样本应至少覆盖以下模板来源：

- **CAN/CAN FD 台架工具界面**：PCAN-View、CANoe、CANalyzer、Kvaser 等报文/信号
  列表；
- **SCADA/HMI 画面**：报警表、趋势图、设备状态页；
- **监控与告警面板**：Grafana、Zabbix 的表格/指标面板；
- **终端/日志/数据库结果表**：docker ps、kubectl get pods、MySQL/PostgreSQL 查询
  结果等。

每类出"清晰"与"噪声"两组（噪声 = 缩小、灰底、压缩失真、轻微模糊），中英混排
（信号名英文、注释中文），数值列含十六进制与十进制混排。

### 9.2 v5 升级触发判据

触发条件分两类：

- **识别质量触发**：在真实样本验收中，若数值字段 exact-match、WERR 或 CER 低于
  标定后的门槛，则优先将 **rec** 模型升级至 v5；
- **检测质量触发**：若列归属准确率、单元格漏检率低于标定后的门槛，且分析确认
  为检测框缺失或列缝断裂导致，则评估升级 **det** 模型。

具体门槛数值**待真实样本标注完成后标定**，不在本阶段提前固化。

### 9.3 列还原（已实现）与扰动要求

列还原与引擎无关，放在 `crates/lumelog-core/src/ocr.rs`：

1. **分行**：按纵向重叠归行（容差 0.5 倍字高，兼容一行内字号不一）；
2. **找列缝**：合并全部词的 x 区间取空隙，只保留同时满足三条的：绝对宽度 ≥6px、
   ≥1.5 倍**字符宽度**、且跨行重复出现（默认 ≥2 行且 ≥30% 行）。
   - 第 2 条按**字符宽度**而不是词宽度：中文标签是"几个字"宽，按词宽算会把阈值
     抬到真实台架表格根本没有的量级（4 个汉字的标签词宽≈60px，阈值就变成 90px，
     而真实表格的列缝只有 20–40px）；
   - 第 3 条是为了不把日志行里等宽词距误判成列（日志行没有列，表格才有列缝）；
3. **填格**：每个词按水平中心落到某一列，格内多词用空格连接；**相接的框（间隙
   ≤2px）直接拼接不插空格**——检测器把一个词切成两半时，"1200" 才不会变成
   "12 00"。

**可信词（Phase 0.5 的扰动防护）**：算列缝时只信"在别的行里也有同位置词"的框
（按 x 对齐聚类，出现在 ≥2 行的簇才算列位置）。孤立噪声框（边框线、噪点）因此
不会把一条列缝切成两半、导致列边界丢失；噪声框本身仍参与填格。

```rust
let g = lumelog_core::ocr::grid(&words);   // 词框 → 行列网格
g.column_count();                           // 4
g.column_values(1);                         // ["Signal", "MotorSpeed", "MotorTorque"]
g.column_text(2);                           // "Value\n1200\n340" —— 落新标签页
```

## 10. 风险

1. **识别率**：中文表格截图上 PP-OCR 明显强于 Tesseract；小字号、压缩失真、反光
   照片会掉点。需要真实样本实测，不能拍脑袋。
2. **列还原的边界情况**：表格有竖线、合并单元格、格内换行、稀疏列时，列缝可能连不
   成直线。当前是几何法 + 对齐聚类，复杂表格要靠"用户手动指定列边界"兜底。
3. **噪声框切细列**：落在列内部的噪声框会把该列切成两列（值不丢，列被切细），
   表现为列选择器里多出一列窄列。
4. **跨平台不一致**：三平台引擎不同，质量不同。PP-ONNX 作为保证路径把差异收窄，
   但系统引擎仍会更快。
5. **不是所有图都适合**：图形/曲线/波形转不了文字（那是另一条图像分析的线）。

## 10.2 PP-ONNX 实测结论（组件产出后）

组件构成（实测）：`onnxruntime` 1.31.1 原生库 18.4MB + `ch_PP-OCRv4_det_infer.onnx` 4.5MB
+ `ch_PP-OCRv4_rec_infer.onnx` 10.4MB + `ppocr_keys_v1.txt` 26KB，合计 **33.3MB**，
打包 zip 20MB。模型来自 RapidOCR 发布的 PP-OCRv4 ONNX 转换件，字典来自 PaddleOCR 官方仓库。

端到端跑通（`LUMELOG_OCR_COMPONENT` 指向组件目录 + `engine=onnx`）：识别 243 词框、
10 行、8 列。**文字全部正确**（`BatteryVoltage`、`BrakePressure`、`GearPosition`、
`EngineRpm`、中文表头「名称 / DLC / 数据 / 周期（ms）」都对，比 Windows 内置引擎的
错识少得多——Windows 把 `Voltage` 读成 `V01tage`、把周期列整列漏掉）。

三个必须记下的实现约束（都是实测得来的）：

1. **DB 检测是行级的**：整张表格的一行被当成一个"文本行"（500×24px）。识别器只有
   48×320 的输入，长行会被压扁，CTC 时间步摊到 500px 上 → 每步 12.5px，字符位置全糊。
   → 改成**按模型最大宽高比（320/48 ≈ 6.7:1）切块**再识别，位置精度回到 ≈4px/步。
2. **CTC 的 blank 不是词边界**：这个中文模型的字符之间也有 3–4 个 blank（实测
   `[0,0,0,0,0,0,1310,0,0,0,0,4244,…]`），按 blank 分词会把 `MotorSpeed` 拆成
   单字。→ 改为按 **CTC 峰值位置**（非 blank 步）定位字符，位置是有意义的（实测
   「名」第 3 步、「称」第 9 步 ↔ 图上相距约 17px）。
3. **峰值定位的分辨率有限**：切块后仍只有 ≈4px/步，而拉丁字母宽约 9px → 量化误差
   ±4px，**已经接近字母间距本身**，因此 PP-ONNX 路径无法稳定区分"字母间距"与"词间距"：
   拉丁词内会出现多余空格（`M otorSp eed`），列数也因此偏多（8 而非 5）。中文不受影响
   （汉字宽 16px ≫ 4px）。

### 10.2.1 像素级列分割（Phase 1.5，已落地）

靠 CTC 峰值拿不到可靠的字内间距，所以**列结构改到像素里找**：二值化 → 剔除表格
横线 → 找列缝 → 按列切条 → 每条单独识别（`app/src-tauri/src/ocr/columns.rs`）。
列一旦由像素定死，识别器就不必再做字符级定位，整行文本原样入格 → **文字不再有
多余空格**（此前 `M otorSp eed`，现在 `MotorSpeed`）。

判据换过三轮，每一轮都被真图证伪：

1. **按像素计数判空隙** → 错：窄字形（"0"）留下大片空白，"00 00 00 00" 整段被当成
   一条巨大列缝（实测把数据列截成 321..384，内容丢一半）。
2. **按墨迹段计数 + 固定像素阈值** → 错：值内的对齐间隙与真列缝在几何上同构，
   只有宽度可依，而阈值对不同表格内容敏感（4.5×块宽仍把 44px 的真列缝切掉）。
3. **最终判据：列对齐** —— 真列缝右侧第一个墨块的**起点**在多行上相同（列的左边界
   严格对齐）；值内的间隙逐行错开（"00 1A 2B" vs "00 00 00 64"）。左边界用起点而
   不是右边界：右边界会随字形抖动（"00" 的墨比 "64" 宽几像素）。再叠加"至少两行
   同意"（一行可能碰巧对齐）与"间隙宽度 ≥ 12px"。

实测（`can-tool-clean.png`，PP-ONNX 路径）：**5 列 × 10 行，与真表一致**；
文字 `MotorSpeed` / `MotorTorque` / `BatteryVoltage` / `CoolantTemp` / `AmbientTemp`
/ `EngineRpm` / 中文表头「名称 / 数据 / 周期（ms）」全部正确。

残余问题（属识别质量，不是列结构）：数据列尾部的 `00 00 00 00` 仍会被切块裁掉，
个别词少/多一个字母（`BrakePresslure`、`GearPositioon`）。系统引擎在同一张图上
5 列精确、逐字框、文字干净——**表格场景仍以系统引擎为首选**，PP-ONNX 是保证路径。
