# 图片转文字（本地 OCR）+ 列还原 + 选列提取：可行性调研

调研目标：把截图（台架工具、CAN 分析仪、测试报告的表格）转成文本，**保持列结构不变**，
再让用户**挑其中一列**的数据取出来。不调用大模型，全程本地离线。

结论：**能做，且不需要大模型。** OCR 是传统 CV 模型（文本检测 + 序列识别），
本地跑得动；真正有难度的是"列还原"和"跨平台引擎选型"，前者已在
`lumelog-core::ocr` 里做完技术验证（见 §4）。

## 1. 为什么不需要大模型

- OCR 的工作流是"检测文本框 → 裁剪 → 逐框识别字符"，模型是几 MB 到几十 MB 的
  CNN/CRNN，不是自回归语言模型。没有"理解上下文"这一步，也不需要联网。
- 仓库里已有 AI 面板（OpenAI 兼容接口，`ai.rs`），但这条链路明确不依赖它：
  断网、离线、无 API key 都要能跑。
- 代价要认：OCR 是"看图猜字"，错字率明显高于大模型视觉。对工控场景（信号名、
  数值、单位）够用，对长句散文不够用。

## 2. 本地引擎候选

| 路线 | 中文 | 体积 | 跨平台 | 离线 | 备注 |
|---|---|---|---|---|---|
| Windows.Media.Ocr | 需 OCR 语言包（中文版 Windows 一般自带 zh-Hans） | 0（系统自带） | 仅 Windows | 是 | `windows` crate 有 `windows::Media::Ocr::OcrEngine`；逐词带矩形框；有 `MaxImageDimension`（超限要缩放） |
| macOS Vision | 内置，`recognitionLanguages` 首位给 zh-Hans | 0 | 仅 macOS | 是 | `objc2-vision` 的 `VNRecognizeTextRequest`；逐词带框；WWDC25 另有读表格的 `RecognizeDocumentsRequest` |
| PP-OCR（ONNX） | 强（开源中文最好那档） | 模型需随包或下载 | 三平台一致 | 是 | `ort`/`candle` 运行时 + PP-OCRv4/v5 ONNX；det+rec 模型量级几 MB 到十几 MB（待实测） |
| Tesseract | 一般（chi_sim 识别率明显低于 PP-OCR） | `chi_sim` fast 约 2.5MB + 引擎本体 | 三平台（需 C++ 依赖） | 是 | TSV 输出逐词带框；`tesseract` crate 要编 C++，`leptess` 可静态编 |

三条 OS/引擎路线的**输出格式可以统一**：都是"词 + 像素框"。所以引擎是可替换的，
列还原算法与引擎无关——这是把核心算法放在 `lumelog-core`、把引擎放在 app shell 的原因。

Linux 没有系统 OCR 是唯一缺口：Linux 版走 PP-OCR ONNX，和其他平台行为一致。

## 3. 输入是什么

用户给的是图片文件（截图）。Rust 侧用 `image` crate 解码（纯 Rust，无原生依赖），
再做预处理（灰度、二值化、按需放大）。已有前端 canvas 渲染 PDF 的经验可复用，
但 OCR 必须拿原始像素，所以解码放 Rust 侧。

## 4. "列不变"怎么做（已完成技术验证）

所有引擎都给词框，不给列。列还原按三步走，`crates/lumelog-core/src/ocr.rs` 已实现：

1. **分行**：按纵向重叠把词归到行（容差 0.5 倍字高，兼容一行内字号不一）；
2. **找列缝**：把全部词的 x 区间合并，得到的空隙里，只有同时满足三条的才算列边界——
   绝对宽度 ≥ 6px、≥ 1.5 倍"中位词宽"、且在多行里重复出现（默认 ≥2 行且 ≥30% 行）；
   第 2、3 条是为了不把日志行里等宽词距误判成列（日志行没有列，表格才有列缝）；
3. **填格**：每个词按水平中心落到某一列，格内多词用空格连接。

产出的 `Grid` 带行、列跨度、单元格文本，可以导出 TSV、空格对齐文本，或**直接取一列**：

```rust
let g = lumelog_core::ocr::grid(&words);      // 词框 → 行列网格
g.column_count();                              // 4
g.column_values(1);                           // ["Signal", "MotorSpeed", "MotorTorque"]
g.column_text(2);                             // "Value\n1200\n340" —— 可直接粘进编辑器
```

验证：`cargo test -p lumelog-core --lib ocr::` 6 例（表格保列、格内多词合并、
日志行不误判、列只在部分行出现、TSV/对齐文本输出、越界列返回空）。
性能：`cargo bench -p lumelog-core --bench ocr_grid`，400 行 × 8 列（9600 词框）
重建 **1.04ms**（`[1.0208 ms 1.0378 ms 1.0569 ms]`）——相对 OCR 的秒级可忽略。

## 5. "选某一列"的数据流

```
图片 → Rust 解码 → OCR 引擎（词框） → lumelog-core::ocr 还原行列 → 前端出列选择器
                                                                     ↓ 选第 N 列
                                          column_text(N) → 新文档 / 插入当前光标 / 替换选区
```

前端交互建议：识别完成后开一个 dock，左边是原图（带框），右边是还原出的表格，
表头列出各列（取第一行或用户指定行为表头），点列头即选中该列，下方预览该列文本，
确认后落进编辑器。这跟仓库现有的"解析面板"（ParserPanel）形态一致，可以复用它的
虚拟表格与行跳转。

## 6. 性能预算

沿用 spec §2 的门槛口径，OCR 是**旁路功能**，不进启动路径，不影响 P1–P6：

| 编号 | 指标 | 建议门槛 | 说明 |
|---|---|---|---|
| P7 | 1920×1080 截图识别耗时 | ≤3s（release，Windows 基准机） | 引擎差异大，需按引擎分别记；后台线程跑，UI 不卡 |
| P8 | 列还原耗时 | ≤5ms（400×8 表） | 已实测 1.04ms，门槛留 5 倍余量 |
| P9 | 识别期间内存增量 | ≤300MB | 解码后的位图 + 引擎模型；1080p RGBA 约 8MB，不是问题，模型才是 |
| — | 取消响应 | 取消后 ≤200ms 停止 | 参照 `can_cancel` 的取消通道 |

执行方式沿用仓库既有模式：`spawn_blocking` 里跑，通过 Tauri `Channel` 回传进度
（`doc_chunk`、`can_parse` 都是这个套路），前端能取消。

## 7. 体积约束（P6）

P6 是 Windows 安装包 ≤15MB，现在 5.66MiB。

- 走 OS 内置引擎（Windows/macOS）：**+0MB**，不破门槛；
- 走 PP-OCR ONNX：模型几 MB 到十几 MB，随包会顶到门槛边缘 → 建议**首次使用时按需下载**
  到 `$APP_CONFIG`（和插件同思路），或者单独做一个"OCR 组件"安装包；
- 走 Tesseract：要编 C++ 引擎本体 + `chi_sim` 数据，同样建议按需下载。

## 8. 风险

1. **识别率**：中文表格截图上 PP-OCR 明显强于 Tesseract；小字号、压缩失真、反光
   照片会掉点。需要真实样本实测，不能拍脑袋。
2. **列还原的边界情况**：表格有竖线、合并单元格、单元格内换行、稀疏列（某行该列为空）
   时，"列缝"可能连不成直线。当前实现是几何法，遇到复杂表格要靠"用户手动指定列边界"兜底。
3. **跨平台不一致**：三平台三套引擎，输出质量不同。要么统一用 ONNX（体积换一致性），
   要么接受平台差异并在 UI 里说明。
4. **不是所有图都适合**：截图里的图形/曲线/波形转不了文字（那是另一条图像分析的线）。

## 9. 建议路线

1. **Phase 0（已做）**：`lumelog-core::ocr` 列还原 + 测试 + bench，引擎无关。
2. **Phase 1**：引擎抽象 `OcrEngine { recognize(image) -> Vec<WordBox> }` 放 app shell；
   Windows 走 `Windows.Media.Ocr`、macOS 走 Vision，各接一个后端 + 单测用固定词框夹具；
   前端先只做"图片 → 文本"（不选列），确认识别率与耗时。
3. **Phase 2**：列选择器 UI + 选列落进编辑器；Linux 用 ONNX 后端补齐。
4. **Phase 3**：可选的预处理（放大、二值化、透视校正）与"表格线检测"兜底。

待你拍板的三件事：
1. 引擎策略——**各平台用系统内置**（省体积、质量好、行为不一致）还是**统一 ONNX**
   （一致、模型要下载）？
2. 输入范围——只吃图片文件，还是也要支持"从 PDF 里选区域 OCR"（PDF 已经有 canvas 渲染，
   但要加框选交互）？
3. 输出落点——选列结果进"新标签页"、"当前光标处插入"、还是"替换当前选区"？
