# 图片转文字（本地 OCR）+ 列还原 + 选列提取：设计与调研

调研目标：把截图（台架工具、CAN 分析仪、测试报告的表格）转成文本，**保持列结构不变**，
再让用户**挑其中一列**的数据取出来。不调用大模型，全程本地离线。

结论：**能做，且不需要大模型。** OCR 是传统 CV 模型（文本检测 + 序列识别），
本地跑得动；真正有难度的是"列还原"、"坐标映射"和"跨平台引擎选型"。列还原已在
`lumelog-core::ocr` 里做完技术验证（见 §8）。

## 0. 已定的决策

| 项 | 决策 |
|---|---|
| 引擎策略 | **混合**：Win/macOS 用系统内置引擎，**PP-ONNX 从"兜底"提升为"保证路径"**——Linux 与"系统内置没有目标语言包"时走 PP-ONNX，且 PP-ONNX 在所有平台都必须可用（见 §3） |
| 输入范围 | **Phase 1 只做图片文件**（PNG/JPEG 等），不做 PDF 区域框选 |
| 输出落点 | **默认落"新标签页"**：选列结果开成新的只读/编辑文档；后续可加"插入当前光标""替换选区" |
| 模型分发 | **方案 B：离线组件包**——模型 + ONNX Runtime 原生库打成独立组件，**离线安装，不做运行时下载**（见 §3.2） |
| OCR 运行时 | **`ort`（ONNX Runtime）**，`load-dynamic` 特性，运行时动态加载原生库（见 §3.2） |
| 运行时依赖集 | **最小集**：v4 mobile det + v4 ch rec + ort 原生库，**det → rec 两段，无 cls、不带 en 单独一套**；v5 留作验收不达标时的升级杠杆（见 §3.3） |
| 样本 | **按公开台架 / CAN 界面造一批仿真样本**作验收 corpus；合成样本另跑 CI 回归（见 §9） |

三条决策背后的同一逻辑：**体积靠"拆分"解决，不靠重定门槛或牺牲可靠性；可靠性靠
成熟实现 + 真实数据兜底，不靠自研运行时或想象中的样本。** 因此 P6（Windows 安装包
≤15MB）不重定，`ort` 带来的体积由组件包隔离出去。

**唯一必须在交付前盯住的连锁假设**：组件包必须是**离线可装**的。工控现场常常
无外网，如果 PP-ONNX 依赖运行时下载，整条链路的可用性会被一次性拖死——所以
组件包要能在断网的干净机器上装完即用（验证清单见 §3.2）。

## 1. 为什么不需要大模型

- OCR 的工作流是"检测文本框 → 裁剪 → 逐框识别字符"，模型是几 MB 到几十 MB 的
  CNN/CRNN，不是自回归语言模型。没有"理解上下文"这一步，也不需要联网。
- 仓库里已有 AI 面板（OpenAI 兼容接口，`ai.rs`），但这条链路明确不依赖它：
  断网、离线、无 API key 都要能跑。
- 代价要认：OCR 是"看图猜字"，错字率明显高于大模型视觉。对工控场景（信号名、
  数值、单位）够用，对长句散文不够用。

## 2. 输入与输出（Phase 1）

- 输入：图片文件。Rust 侧用 `image` crate 解码（纯 Rust，无原生依赖）。
- 输出：选中的那一列 → `column_text(col)` → **开成新标签页**（可编辑、可保存）。
  同时保留"整表"视图（TSV / 空格对齐），方便核对。

## 3. 引擎策略：混合 + PP-ONNX 为保证路径

### 3.1 三条引擎路线

| 路线 | 中文 | 体积 | 跨平台 | 逐词置信度 | 备注 |
|---|---|---|---|---|---|
| Windows.Media.Ocr | 需 OCR 语言包（中文版 Windows 一般自带 zh-Hans） | 0（系统自带） | 仅 Windows | **无**（`OcrWord` 只有 `Text` + `BoundingRect`） | `windows` crate 有 `windows::Media::Ocr::OcrEngine` |
| macOS Vision | 内置，`recognitionLanguages` 首位给 zh-Hans | 0 | 仅 macOS | 有（`VNRecognizedText.confidence`） | `objc2-vision` 的 `VNRecognizeTextRequest` |
| PP-OCR（ONNX） | 强（开源中文最好那档） | 模型需随包或分发 | 三平台一致 | 有（识别器逐行分数） | `ort` 运行时 + PP-OCRv4/v5 ONNX；det+rec 模型量级几 MB 到十几 MB（待实测） |

三条路线的输出都能统一成"词 + 像素框"，所以引擎可替换，列还原算法与引擎无关。

### 3.2 分发方案 B（已定）：离线组件包

**保证**：任何一台装了本版本的机器上，PP-ONNX 都必须能跑——不依赖系统语言包、
不依赖用户手动点下载、离线也能用。Linux 只有这一条路，所以它不能是"平时用不上、
出问题再下载"的兜底；Windows/macOS 上它也必须随时可切（例如系统语言包缺失、
识别质量差需要对比、用户就想强制指定引擎）。

达成方式（**已定：方案 B**）：

把"模型 + ONNX Runtime 原生库"打成一个**独立组件包**，**离线安装，不做运行时下载**。

组件包内容：

    ocr-component-<ver>/
      manifest.json        # 版本、SHA-256 清单、模型清单、许可证
      bin/onnxruntime.dll  # Windows（Linux .so / macOS .dylib）
      models/ch_PP-OCRv4_det_infer.onnx   # 检测（mobile）
      models/ch_PP-OCRv4_rec_infer.onnx   # 识别（ch，中英数一体）

- **主包不装原生库**：用 `ort` 的 `load-dynamic` 特性，只在真正要跑 PP-ONNX 时才
  `ort::init_from(<组件目录>/onnxruntime.dll)` 动态加载。ONNX Runtime 的体积因此
  完全留在组件包里，**主安装包体积不受影响，P6（≤15MB）不重定**。
- **组件缺失时主程序照常启动**：原生库只在调用 PP-ONNX 时才加载，缺失只是
  "该引擎不可用"，不影响编辑器其它功能。
- **安装形态**：独立安装包或 zip（U 盘 / 内网 / 工控机离线拷贝均可），装到约定
  目录（建议 `<安装目录>/ocr/<组件版本>/`；Linux 走 tar.gz，解压即用）。
- **完整性**：安装后按 `manifest.json` 校验 SHA-256，校验不过拒绝启用该引擎。

**交付前必须逐条验证的清单**（这条是整条链路的可用性命门）：

1. **断网干净机**：在一台**没有外网**的干净机器上装组件包 → 装完即用，能识别出
   中文表格。这是"离线可装"的硬验证，不是走过场；
2. **三平台各一份**：Windows/Linux/macOS 的原生库名不同，组件包要分别产出；
3. **主包体积**：加完组件后主安装包仍 ≤15MB（P6 不重定，CI 产物检查）；
4. **缺失可用**：不装组件时主程序正常启动，PP-ONNX 选项显示"未安装组件"，提示
   指向本地安装包位置而不是网络下载链接；
5. **模型与许可证**：PP-OCR 模型（Apache-2.0）与 ONNX Runtime（MIT）的版本、来源、
   SHA-256 写进 `manifest.json` 与发布说明。

运行时（**已定**）：`ort`（ONNX Runtime 1.31，成熟实现；`ort` crate 当前
2.0.0-rc.15，许可 MIT OR Apache-2.0）。RC 版本的版本在 `Cargo.lock` 里钉死，ORT
相关代码收在单独模块里，避免升级牵连其它部分。

### 3.3 运行时依赖集（已定，最小集）

组件包里只有三个东西：

| 组件 | 文件 | 说明 |
|---|---|---|
| 文本检测 | `ch_PP-OCRv4_det_infer.onnx`（mobile 版） | 几 MB 级 |
| 文本识别 | `ch_PP-OCRv4_rec_infer.onnx`（ch 版） | 几 MB 级；中英数一体 |
| 推理运行时 | `bin/onnxruntime.dll`（Linux `.so` / macOS `.dylib`） | `ort` 动态加载 |

砍掉的，逐条有理由：

- **cls（方向分类器）**：输入恒为 upright（软件界面截图、PDF 选区），不存在旋转
  行。它带来的是体积（离线组件包里每一 MB 都是装机成本）、多一次分类推理的延迟
  （撞 P7/P8），以及更糟的误判风险——短数字串（1200）在小图块上被判成 180°，
  等于把好认的值认翻，主动制造静默错误。管线定成 **det → rec 两段**。
- **en 单独一套**：PP-OCR 的 ch 模型本身中英数一体（训练就覆盖中英文 + 数字），
  不是"纯中文模型"；en 只在纯英文场景且要把体积压到极致时才值得考虑。
- **server det**：手机版 det 在台架/CAN 界面截图上够用，server 版体积换不来收益。
- **v5**：首发用 v4。v5 是**验收不达标时的升级杠杆**——届时只换 rec 一个文件，
  det 不动。

相对"v4/v5 各来一套中英 + cls + server det"的贪婪配置，这套收敛到
**两个模型 + 一个运行时**，是离线组件包（B 方案）能接受的大小。

### 3.3 引擎选择顺序（决策表）

```
用户显式指定引擎？ ──是→ 用它（不可用则报错并列出可用引擎）
        │否
        ▼
目标语言的系统引擎支持？ ──是→ 系统引擎（Win: Windows.Media.Ocr / mac: Vision）
        │否（Windows 缺 zh-Hans 语言包 / Linux 无系统引擎）
        ▼
OCR 组件包已安装？ ──是→ PP-ONNX（ort 动态加载组件里的原生库）
        │否（组件未装；不做运行时下载）
        ▼
降级：系统默认语言引擎（多半是英文）能认多少算多少 + 明确提示
      「中文识别不可用：系统缺 zh-Hans OCR 语言包，OCR 组件包未安装（<组件目录>）」
```

UI 上给引擎切换入口（自动 / 系统内置 / PP-ONNX），便于对比与排障；PP-ONNX 缺失时
提示里直接给下载或"装离线组件"的入口。

## 4. 坐标映射

唯一真值是**原始解码后的图像像素坐标系**（EXIF 方向已归一化）。所有引擎适配层
必须把框还原到这个坐标系，前端只做一次显示缩放。

### 4.1 解码期归一化

- EXIF 方向：`ImageReader::open(path)?.into_decoder()?` → `decoder.orientation()?`
  → `DynamicImage::from_decoder(decoder)?` → `image.apply_orientation(orientation)`
  （`image` 0.25 具备这两个 API）。归一化之后，解码出的像素矩阵与用户看到的方向
  一致，之后所有坐标都基于它。
- 尺寸上限：`Windows.Media.Ocr` 有 `OcrEngine.MaxImageDimension`（运行时读该属性，
  Windows 上通常是 4096）。超限必须先缩放，识别后把框坐标除以缩放系数还原。

### 4.2 引擎坐标系的还原

- **Windows.Media.Ocr**：`OcrResult.TextAngle` 是文字整体倾斜角，而
  `OcrWord.BoundingRect` 落在**去偏斜后**的坐标系里。映射回原图要绕图心做一次
  反向旋转；`TextAngle` 为 0 时直接用。
- **PP-ONNX**：检测输出四点框 → 取轴对齐外接矩形；检测带角度的先按角度校正，
  再把外接框换算到原图坐标。
- **Tesseract**：TSV 的 `left/top/width/height` 已是原图像素（列分析不影响框坐标）。

### 4.3 显示层映射

- dock 里图片按 fit/zoom 显示：`显示坐标 = 原图坐标 × (显示宽 / 原图宽)`。
  HiDPI 的 DPR 只影响 CSS 像素↔设备像素，不参与图片内坐标换算。
- 定义单一映射对象（示例）：`ImageMapping { src_w, src_h, scale }`，提供
  `to_image(x, y)` / `to_display(x, y)`。前端叠加识别框、点选区域都用它，
  不允许各处自己乘系数。
- 取整策略：列边界在**原图坐标**里算完，再按 display scale 缩放到显示层；不在
  显示层做取整，避免误差累积。

### 4.4 验收

- 单测：EXIF 旋转 90°、缩放 0.5、Windows 去偏斜 3° 三个映射用例（用构造的框验证
  往返一致，误差 ≤1px）。

## 5. 识别置信度与纠错

### 5.1 各引擎的置信度能力

| 引擎 | 逐词置信度 |
|---|---|
| Windows.Media.Ocr | **没有**（`OcrWord` 只暴露 `Text` 与 `BoundingRect`） |
| macOS Vision | 有（`VNRecognizedText.confidence`） |
| Tesseract | 有（TSV 逐词 `conf`，0..100；非词层级为 -1） |
| PP-ONNX | 有（识别器逐行/逐字分数） |

统一模型：`WordBox.conf: Option<f32>`（0..=1，`None` = 引擎不提供）。Windows 路径
没有逐词置信度，因此下面的策略必须能在"没有置信度"时退化工作。

### 5.2 阈值与标记

- 逐词低置信阈值默认 0.6（设置可调）；低于阈值的词在 UI 上标黄。
- 整图置信度 = 有置信度时取加权平均；低于 0.5 时提示「识别质量低，建议重新截图」。
- Windows 路径没有置信度 → 退化用**列类型校验**（见下）作为主要质量信号，
  并在 UI 上注明「此引擎不提供置信度」。

### 5.3 纠错手段（都不用大模型）

1. **人工改**：OCR dock 的表格里直接改单元格，保留原值与修改痕迹。
2. **列类型校验**：按列推断类型（整数 / 浮点 / 十六进制 / 布尔 / 时间戳），
   不匹配的单元格标红。工控表格多是数值与 hex，这招比置信度更实用。
3. **易混字符提示**：数值列里出现 `O l I S B Z` 等 → 提示可能混淆；**只提示不自动改**，
   避免把对的改错。
4. **导出时过滤**：可选「只导出高置信单元格」或「低置信行单独列出」。

### 5.4 职责边界

`lumelog-core::ocr` 保持纯函数、**不做任何猜测性修正**；修正与过滤放在 app shell
层。`column_text()` 给的是原样文本。

## 6. 语言包 fallback

- 语言设置：`自动`（默认，跟随系统）/ `简体中文` / `English`，持久化在设置里。
- 检测方式：
  - Windows：`OcrEngine::AvailableRecognizerLanguages` /
    `OcrEngine::IsLanguageSupported(Language)`；
  - macOS：Vision 的 supported recognition languages；
  - PP-ONNX：组件包存在 + `manifest.json` 的 SHA-256 校验通过 + 该语言模型在清单里。
- fallback 链（与 §3.3 一致）：目标语言的系统引擎 → PP-ONNX（组件包已装）→ 系统
  默认语言引擎（多半英文，能认多少算多少）+ 明确提示 → 彻底不可用时报错。
- 提示要具体到可执行：「系统缺 zh-Hans OCR 语言包」/「OCR 组件包未安装，路径
  `<组件目录>`，用离线安装包装上即可」，而不是笼统的"识别失败"，也**不给网络下载
  链接**（工控现场常常无外网）。
- Windows 上装了中文语言包也不代表识别质量够用（截图小字、压缩失真都会掉点），
  所以引擎切换入口始终可用。

## 7. 性能预算

沿用 spec §2 的门槛口径；OCR 是**旁路功能**，不进启动路径，不影响 P1–P6：

| 编号 | 指标 | 建议门槛 | 说明 |
|---|---|---|---|
| P7 | 1920×1080 截图识别耗时 | ≤3s（release，Windows 基准机） | 按引擎分别记；后台线程跑，UI 不卡 |
| P8 | 列还原耗时 | ≤5ms（400×8 表） | 已实测 1.04ms，留 5 倍余量 |
| P9 | 识别期间内存增量 | ≤300MB | 1080p 位图约 8MB；模型才是大头 |
| P10 | 主安装包体积（加组件后） | ≤15MB（P6 不重定） | ONNX Runtime 与模型都在组件包里，主包不涨 |
| — | 取消响应 | 取消后 ≤200ms 停止 | 参照 `can_cancel` 的取消通道 |

执行方式沿用仓库既有模式：`spawn_blocking` 里跑，通过 Tauri `Channel` 回传进度
（`doc_chunk`、`can_parse` 都是这个套路），前端可取消。

## 8. 列还原（已实现）

所有引擎都给词框、不给列，所以这一层与引擎无关，放在 `crates/lumelog-core/src/ocr.rs`：

1. **分行**：按纵向重叠归行（容差 0.5 倍字高，兼容一行内字号不一）；
2. **找列缝**：合并全部词的 x 区间取空隙，只保留同时满足三条的：绝对宽度 ≥6px、
   ≥1.5 倍中位词宽、且跨行重复出现（默认 ≥2 行且 ≥30% 行）。第 2、3 条是为了不把
   日志行里等宽词距误判成列（日志行没有列，表格才有列缝）；
3. **填格**：每个词按水平中心落到某一列，格内多词用空格连接。

```rust
let g = lumelog_core::ocr::grid(&words);   // 词框 → 行列网格
g.column_count();                           // 4
g.column_values(1);                         // ["Signal", "MotorSpeed", "MotorTorque"]
g.column_text(2);                           // "Value\n1200\n340" —— 落新标签页
```

验证：`cargo test -p lumelog-core --lib ocr::` 6 例；性能
`cargo bench -p lumelog-core --bench ocr_grid` → 400 行 × 8 列（9600 词框）重建
**1.04ms**（`[1.0208 ms 1.0378 ms 1.0569 ms]`）。

## 9. 样本端到端验收

验收 corpus = **按公开台架 / CAN 工具界面造的仿真样本**（版面取自公开的台架软件与
CAN 分析仪界面），每张图配一份生成时就知道的真值；另有合成样本专跑 CI 回归。

- **仿真样本（验收依据）**：按公开界面布局渲染的表格截图 + 逐格真值。覆盖三类：
  CAN 分析仪报文表（ID / 名称 / DLC / 数据 / 周期）、台架日志窗口（时间 / 级别 /
  线程 / 正文）、测试报告表（步骤 / 项目 / 期望 / 实测 / 结论）。每类出"清晰"与
  "噪声"两组（噪声 = 缩小、灰底、压缩失真、轻微模糊）。
- **合成样本（CI 回归用，不作为识别质量依据）**：固定字体渲染的规整表格，主要回
  归**列还原与取列逻辑**；清晰合成图上 OCR 近乎完美，字符错误率没有区分度。

### 9.1 仿真样本要求

- 数量 ≥20 张，三类界面各覆盖清晰/噪声两组；
- 中英混排（信号名英文、注释中文），数值列含十六进制与十进制混排；
- 真值逐格给出（TSV），并额外记录**每个词的像素框**——这样"列还原"这一段可以
  在没有 OCR 引擎的情况下先被 CI 验证（用真值词框喂 `lumelog-core::ocr`，断言
  还原出的表格与真值一致）。

### 9.2 门槛（对仿真样本 corpus 生效）

| 指标 | 门槛 |
|---|---|
| 字符错误率 CER（清晰截图） | ≤2%（按引擎分别记） |
| 字符错误率 CER（噪声截图） | ≤5% |
| 单元格完全正确率 | ≥98% |
| 列还原正确率 | 仿真 corpus ≥95%（真值词框直喂时应为 100%） |
| 取列结果与真值逐行相等 | ≥99% |
| 识别耗时 P7 | ≤3s（1080p） |
| 列还原耗时 P8 | ≤5ms |
| 内存增量 P9 | ≤300MB |

（日后若拿到真实设备截图，并入同一 corpus、同一套门槛。）

### 9.3 评测工具与流程

- 工具 `lumelog-ocr-eval`（core 的 bin 或独立 crate）：输入「图片 + 真值 TSV」，
  输出 CER / 单元格准确率 / 列还原结果 / 耗时，产出与 `case-gate.js` 同风格的
  Markdown 报告。
- CI 跑合成样本（回归列还原与取列）与仿真 corpus 的词框直喂检查；识别质量报告
  按引擎跑仿真 corpus，**验收结论以该报告为准**。
- **保证路径验收**：在没装 zh-Hans OCR 语言包的 Windows 上（或用
  `LUMELOG_OCR_ENGINE=onnx` 强制后端），PP-ONNX 必须达到同样的门槛。
- **离线验收**：断网干净机上装完组件包后跑一遍仿真 corpus（这是组件包"离线可装"
  的连带验收，见 §3.2 清单第 1 条）。
- 验收结果写进 `docs/test-checklist.md`（沿用 P1–P10 表格口径），每条记
  引擎、语言、机器、实测数字。

## 10. 风险

1. **识别率**：中文表格截图上 PP-OCR 明显强于 Tesseract；小字号、压缩失真、反光
   照片会掉点。需要真实样本实测，不能拍脑袋。
2. **列还原的边界情况**：表格有竖线、合并单元格、格内换行、稀疏列时，列缝可能连不
   成直线。当前是几何法，复杂表格要靠"用户手动指定列边界"兜底。
3. **跨平台不一致**：三平台引擎不同，质量不同。PP-ONNX 作为保证路径把差异收窄，
   但系统引擎仍会更快。
4. **不是所有图都适合**：图形/曲线/波形转不了文字（那是另一条图像分析的线）。

## 11. 路线与待办

1. **Phase 0（已做）**：`lumelog-core::ocr` 列还原 + 单测 + bench（引擎无关）。

   "真值词框直喂列还原"的断言——把列还原这一段在没有引擎的情况下先钉死。
